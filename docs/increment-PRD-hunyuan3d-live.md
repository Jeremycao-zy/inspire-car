## 0. 需求来源（用户原话）

> 「能接入真正的3D模型。需要真正的实现图生3D模型的功能，需要我做什么？注册什么账号？干什么？」

翻译成产品语言：**用户不知道"要真的用起来"到底需要他做什么，也不知道点了之后会发生什么、要花多少代价、失败了怎么办。**

本次 PRD 的目标不是改生成算法（算法侧已经是现成的混元 3D），而是把「能不能用 / 怎么用 / 用了会怎样」这三件事对用户说清楚、做扎实。

### 1.2 与 README 冲突 / 文档待修项

| # | 冲突点 | 实际情况 |

### 1.3 关键约束：凭证无法在服务端自动刷新

- tempToken（`tk_` 开头）由 IDE 会话下发，**约 16 小时后过期**。
- **过期时间可以精确拿到**：凭证返回体中带 `tempTokenExpiresAt` 字段，值为 ISO8601，例如 `2026-08-30T12:47:03Z`。tempToken 本身（`tk_` 开头）不是 JWT、从字符串里解析不出时间，但**过期时间是从返回里直接读的，不需要解析 token**。
- **但服务端拿不到新凭证**：凭证获取能力**绑定在 IDE 会话 / 助手侧**，平台**没有暴露任何服务端可调用的 HTTP 刷新接口**。也就是说，`server/index.mjs` 这类服务端代码无论如何都拿不到一张新票——这不是"场景对不对"的问题，是**通道根本不存在**。

> ⚠️ **易错点（务必注意）**：不要把这个约束理解成"换个调用场景 / 加个参数就能让服务端自己刷新"。曾有人按这个错误理解去尝试，白花时间。**凭证只能由助手侧获取后写入文件，服务端只能读，不能续。**

→ 这直接决定了决策点 ① 的选型：**只能做"热更新免重启 + 到期提醒 + 引导换票"，不能做"自动刷新"。**

## 2. 六个决策点（本次 PRD 核心结论）

### 决策 ① 凭证生命周期

> **结论：不做自动刷新（技术上不可行）；做「热更新免重启 + 有效期软提醒 + 失效精准识别 + 可执行修复指引」。用户实际只需 1 个动作：把新 token 写进文件（一条命令）。**

| 场景 | 产品行为 |
|---|---|
| 未配置凭证 | 保持 DEMO；状态卡给「如何开启真实生成」三步指引 |
| 凭证有效 | LIVE 状态卡显示**预计过期时间**（优先读取 token 文件携带的 `tempTokenExpiresAt` 精确值；缺失时降级为凭证文件 mtime + 16h 估算，软提醒，不硬判断） |
| 临近过期（< 2h） | 状态卡转黄提示「凭证将在约 X 小时后过期」 |
| 已失效 | **不显示笼统"生成失败"**：识别为凭证类错误，弹出三步修复指引 + 「我已更新，重试」 |
| 用户换新 token | 写入文件即可，**无需重启服务**（依据 D1）；点「我已更新」→ 重新 `/api/health` → 自动转 LIVE |

**用户需要做的动作（正面回答用户原话"需要我做什么"）**：

```
1. 在 IDE 会话中重新获取 tempToken（tk_ 开头）      —— 不用注册任何账号
2. 执行：npm run token -- tk_xxxxxxxx              —— 一条命令写入，不用手敲路径
3. 页面上点「我已更新」                              —— 不用重启服务
```

**不做的事**：不做网页表单粘贴输入 token（会把凭证写进浏览器历史/日志，且本项目是本地单机应用，文件方案更简单安全）。

---

### 决策 ② 多视角要不要做

> **结论：本期不做多视角（降级 P2），但必须先把「传多张只用第一张」的欺骗性行为修掉——改成「多传 = 供你挑，主视角由你点选」。**

**不做多视角的理由**：

| 维度 | 判断 |
|---|---|
| 成本 | `MultiViewImages` 要求**公网可访问 URL** → 必须接对象存储（COS/OSS），引入新依赖、新凭证、新成本项 |
| 风险 | 用户私家车照片要上传到公网可匿名访问的地址，隐私与合规成本显著 |
| 收益 | 本产品核心看点是「轮毂与车身的相对齐平关系」，对几何精度要求没到必须用多视角的程度；单图 base64 已能出可用效果 |
| 替代 | 「多张里挑最好的一张当主视角」几乎零成本拿到 80% 收益 |

**必须做的修正（P0）**：上传后展示全部缩略图，**用户点击指定主视角**，UI 明确标注「选中这张用于生成」。至少 1 张即可生成；多张的意义从"云端会融合"变成"你挑最清晰的那张"。

**保留**：后端 `multiViewJson` 通道不动，前端不暴露。

---

### 决策 ③ 用户上传体验（拍摄引导）

> **结论：上传区新增「怎么拍？」可展开引导，整车 / 轮毂两套不同内容；轮毂明确建议抠图；不强制、不阻断。**

**整车（主视角优先正前 45°）**

| 项 | 要求 |
|---|---|
| 最佳角度 | **正前 45°**（同时看到车头 + 整个侧面，深度信息最足，重建最完整） |
| 可用角度 | 正后 45°、正前、正尾 |
| 应避免 | 纯正侧照（缺深度，车侧面会被拍平）；车头/车尾出框；车轮被裁切 |
| 占比 | 车身占画面 **60% 以上** |
| 光线 | 阴天/散射光最佳；避免正午硬阴影、逆光、夜间闪光灯 |
| 车漆 | 强反光车漆（尤其黑色）明显降低质量，建议避开大面积高光 |
| 背景 | 简洁背景优于杂乱（即使不做抠图也有效） |

**轮毂（建议抠图 / 只拍轮辋）**

| 项 | 要求 |
|---|---|
| 最佳 | **只拍轮辋、抠掉轮胎与车身**，正正面 + 斜 45° 各一张 |
| 为什么 | 后端 prompt 已写 `rim only, no tire, isolated`，但若照片里带胎/卡钳/翼子板，模型仍会把它们建进去，导致 J 值校准失准 |
| 兜底说明 | 「带胎也能生成，之后用 J 值滑杆校正宽度」——**不能因为没有抠图就拦住用户** |
| 应避免 | 车轮着地、轮拱内阴影、刹车卡钳大面积遮挡辐条 |

**通用**：JPG / PNG；长边 ≥ 1024px；单张 ≤ 10MB（前端会压到 1600px / 0.86）。

**UI 形态**：折叠块（默认收起），不弹窗、不阻断选图。

### 决策 ④ 档位与等待

> **结论：面数档位本期不暴露（P1 再以「高级」折叠区给 2 档）；等待态 UI 全面重做；失败分级处置；绝不自动降级到演示模型。**

**4.1 面数**

- P0：维持整车 18w / 轮毂 12w，用户不可调。**修掉 F11 的误导文案**（"降低面数"改为"任务可能仍在云端进行，可继续等待"）。
- P1：在「高级」折叠区加「模型精度：标准 / 高精」，高精 = 面数 ×1.5，标注「更慢、文件更大」。默认标准、默认收起——不污染主路径。

**4.2 等待期 UI（P0，重点改造）**

现状问题（F10）：假进度曲线 + 5 秒一跳 + 暴露内部状态字符串（`状态 RUNNING`）。

新方案：

```
┌ ① 上传整车照片 ────────────────────────────┐
│  [缩略图✓] [缩略图] [缩略图]                │  ← 主视角带 ✓，可点选
│  ▓▓▓▓▓▓▓▓▓▓░░░░░░░░   ← 不确定进度（呼吸动画）│
│  云端建模中 · 已等待 01:23                   │  ← 每秒走字的计时器
│  通常 2–5 分钟，可切走做别的事，回来仍在进行 │
│                              [ 取消生成 ]    │
└──────────────────────────────────────────────┘
```

要求：

1. 进度条在建模阶段改**不确定态（indeterminate）+ 呼吸动画**，不再假装知道百分比；仅「准备照片」「下载模型」用确定态。
2. 文案分四段真语义：`准备照片` → `已提交，排队中` → `云端建模中（已等待 mm:ss，通常 2–5 分钟）` → `下载模型（约 30–45MB）`。
3. 计时器**每秒更新**，证明进程没死。
4. 提供「取消生成」按钮；取消时明确提示：**取消不会终止云端任务，该次额度可能仍会消耗**。
5. 等待期间侧栏其余控件保持可用（滑杆、预设、视角不冻结）。

**4.3 失败分级处置（P0）**

| 失败场景 | 识别依据 | 处置 | 计不计次数 |
|---|---|---|---|
| 凭证失效/未授权 | 网关 `AuthFailure` / `InvalidCredential` / `TokenExpired` / `SignatureDoesNotMatch` 或 HTTP 401/403 | 凭证修复指引 + 「我已更新，重试」；**不自动降级** | **不计** |
| 提交被拒（参数/图片） | 提交阶段其它错误 | 明确原因 + 修正建议 | **不计** |
| 云端生成失败 | 轮询 status ∈ FAIL | 展示云端原因 + 「用同样参数重试」 | 计入失败数，不计消耗数 |
| 轮询超时（12 min） | 超过 `MAX_POLL_MS` 仍未 DONE | **保留 JobId**，提供「继续等待 8 分钟」+「放弃」，不直接判死 | 计入失败数，不计消耗数 |
| 下载失败 | `hy3d.download` 抛错 | **自动重试 2 次**（2s / 6s 退避）——模型已在云端，重试不重复扣额度 | 重试成功则正常计 1 次 |
| 未知异常 | 其它 | 保留上一次成功模型，3D 场景不变，仅侧栏报错 | — |

**核心原则（必须写进验收标准）**：

> **任何失败都不得自动降级到 DEMO 演示模型。** 用户会误以为"我的车生成好了"，这比失败更糟。
> 只在错误态里提供**手动**的「改用演示模型看看效果」按钮，且按钮文案必须带「演示」二字。

### 决策 ⑤ 额度与成本

> **结论：查询不到真实云端余额（待确认 Q3），因此做「本地统计 + 事前预期提示 + 首次 LIVE 确认 + 失败不计次」。**

| 措施 | 说明 |
|---|---|
| 常驻预期提示 | 上传区常驻小字：「单次生成约 2–5 分钟，消耗 1 次云端生成额度」 |
| **首次 LIVE 确认** | 从 DEMO 切到 LIVE 后的**第一次**生成必须先过一次确认。之后不再打断。 |
| 保留全自动 | 确认通过后继续维持「选图即开始」，不加二次点击弹窗（README 的核心卖点）。 |
| 本地计数 | 侧栏显示「已生成 N 次 · 成功 M 次」，数据来源服务端 `.cache/usage.json`（跨刷新保留）。 |
| 失败不计次 | 仅 `stage:done && mode:live` 才 +1 消耗；失败单独计「失败」列；凭证类错误完全不计。 |
| 重复生成提醒 | P1：源图指纹去重，同一组照片重复提交时提示「这组照片已生成过，是否重新生成？」 |

### 决策 ⑥ 生成结果的落地

> **结论：可读命名 + 历史索引 + 侧栏「我的模型」列表 + 一键导出到本地。这是用户"拿到自己车模型"的临门一脚。**

| 措施 | 说明 |
|---|---|
| 可读命名 | `{kind}-{YYYYMMDD-HHmm}-{hash6}.glb`，例：`car-20260829-2145-a1b2c3.glb` |
| 历史索引 | 服务端维护 `.cache/models/index.json`：`{name, kind, size, createdAt, bytes, imageCount, faceCount, jobId}` |
| 「我的模型」列表 | 侧栏新增折叠区，列出历史（时间 / 类型 / 体积），每条带「载入」「导出」按钮。刷新页面不丢。 |
| 导出 | 每条历史带「导出」→ 浏览器下载 GLB 到本地。**用户最想要的产物就是这个。** |
| 删除与清理 | P1：保留最近 20 个；总量超 1GB 时提示清理；支持单条删除。**不静默删除用户成果。** |
| 记住上次 | P1：localStorage 记住上次成功载入的模型，下次启动自动装载。 |

## 3. 产品目标

1. **真实可用**：用户配好凭证后，传自己的照片就能拿到自己车的 GLB；全过程状态可预期、失败可恢复、结果可取回。
2. **诚实不欺骗**：消灭所有「UI 承诺 ≠ 实际行为」的地方——多图只用一张、超时叫你降面数却没有面数、DEMO 冒充真实结果、不知道要花多少钱。
3. **成本可控**：点击之前就知道要花多少时间、多少额度；失败不白花；重复生成不浪费。

## 5. 需求池

> 优先级：P0 = 必须做（本次交付）｜P1 = 应该做｜P2 = 锦上添花
> 每条需求的**验收标准**均写成可观测、可判定（QA 可直接照做验证）的形式。

### 5.1 P0 — 必须做

---

#### P0-1　凭证失效精准识别 + 热更新免重启

**描述**：后端在提交阶段对网关错误分类，把「凭证类错误」与其它错误区分开，通过 SSE 新增 `stage: 'auth_error'` 下发；前端据此展示可执行修复指引。同时确保改凭证文件后**无需重启**即生效。

**验收标准**：

1. 清空/删除 `~/.workbuddy/tokens/hunyuan3d` 内容后在 LIVE 下提交 → SSE 收到 `stage:'auth_error'`，`detail` 含网关原始错误码。
2. 网关返回 `AuthFailure` / `InvalidCredential` / `TokenExpired` / `SignatureDoesNotMatch` 或 HTTP 401/403 时**一律**归为 `auth_error`；其它错误**不得**误归类。
3. 前端收到 `auth_error` 后显示三步修复指引 + 「我已更新」按钮，**不显示**通用"生成失败"文案。
4. **不重启** `npm run dev`，直接写入新 token 文件 → 点「我已更新」→ `/api/health` 返回 `mode:'live'` → 卡片自动转为 LIVE。后端进程 PID 全程不变。
5. 环境变量 `HUNYUAN3D_TOKEN` 与文件同时存在时环境变量优先（维持 F3 不变）。

#### P0-2　凭证状态卡（含有效期软提醒）

**描述**：把现有单行 `mode-badge` 升级为状态卡，区分「LIVE / 临近过期 / 已失效 / DEMO」四态。

**验收标准**：

1. 四态各有独立视觉（LIVE 绿 / 临近过期黄 / 已失效红 / DEMO 灰），文案互不相同。
2. LIVE 态显示预计过期时间，格式如「● LIVE · 凭证预计 8/30 14:20 过期（约 11 小时后）」。
3. 预计过期时间优先读取 token 文件携带的过期时间（精确值）；仅当文件未携带时由**凭证文件 mtime + 16 小时**估算。QA 验证：文件未携带过期时间且 mtime 改为 15 小时前 → 卡片转黄并显示「凭证将在约 1 小时后过期」；文件携带过期时间时直接显示该时刻。
4. 该时间**仅为软提醒**，不得拦截生成（即使算出"已过期"，点击生成仍照常提交）。
5. DEMO 态提供「如何开启真实生成」展开按钮，展开后为完整三步说明（含命令原文，可复制）。
6. 状态卡常驻一行小字：「单次生成约 2–5 分钟，消耗 1 次云端生成额度」。

#### P0-3　首次 LIVE 生成确认

**描述**：首次从 DEMO 切到 LIVE 后的第一次生成必须先确认；通过后后续保持「选图即开始」全自动。

**验收标准**：

1. 确认以**上传区内嵌**形式出现（不是浏览器原生 `confirm`、不是全屏模态），提供「开始生成（消耗 1 次额度）」/「取消」。
2. 确认只出现**一次**。QA 验证：一次成功生成后再上传 → 不再出现确认，直接开始。
3. 「取消」后不提交任何请求（Network 无 `/api/generate`），上传区恢复初始态。
4. 确认状态持久化到 localStorage；清缓存后重新出现（安全性优先于便利性）。
5. DEMO 模式下**从不**出现此确认。

#### P0-4　多图主视角可点选（消除"传 5 张只用 1 张"）

**描述**：上传多张后全部显示缩略图，用户点击指定主视角；UI 明确标注选中项。至少 1 张即可生成。

**验收标准**：

1. 上传 5 张 → 5 张缩略图全部显示；**默认选中第一张**，选中项有清晰的 ✓ 或高亮边框。
2. 点击第 3 张 → 选中态转移；提交后服务端收到的 `images[0].dataUrl` **必须是第 3 张**的内容（QA 用 5 张内容差异明显的图验证，比对服务端 `submit` 日志里的图片大小）。
3. 提示文案改为「**1 张即可生成，多张供你挑选最清晰的一张作为主视角**」。
4. 文案中**必须**明确告知云端只使用选中的那一张（例如「当前仅使用选中的 1 张照片生成」）。
5. 选中态在生成过程中锁定；生成结束（成功或失败）后解锁。
6. 后端 `multiViewJson` 通道保持不动，前端仍不传 `multiView`。

#### P0-5　拍摄引导内容（整车 / 轮毂两套）

**描述**：上传区新增「怎么拍？」折叠块（默认收起），整车与轮毂各一套引导（内容见决策 ③）。

**验收标准**：

1. 两个上传区各自独立折叠块，整车区显示整车引导、轮毂区显示轮毂引导，内容不得串用。
2. 默认收起，点击展开；展开不遮挡上传区本身，不弹窗。
3. 整车引导**必须**包含：最佳角度（正前 45°）、占比 ≥60%、光线要求、应避免项（纯正侧、出框、强反光）。
4. 轮毂引导**必须**包含：建议抠图/只拍轮辋，以及兜底说明「带胎也能生成，之后用 J 值滑杆校正」。
5. 通用要求（JPG/PNG、长边 ≥1024px、单张 ≤10MB）两个引导块都有。
6. 引导**不阻断**选图：即使完全不符合要求，也能正常提交。

#### P0-6　等待态 UI 重构

**描述**：重做生成中反馈——不确定态进度条、每秒走字计时器、分阶段真语义文案、取消按钮。

**验收标准**：

1. `submit` / `polling` 阶段进度条为**不确定态**（呼吸/流动动画），不得出现"百分比 5 秒完全不动"（现状 F10）。
2. 仅 `prepare` 与 `downloading` 用确定态，且进度真实。
3. 已等待计时器格式 `mm:ss`，**每秒更新**（QA 连续观察 3 秒，数字变化 3 次）。
4. 各阶段文案符合 §6.5 四段式，**不得**出现内部状态字符串（`状态 RUNNING`、裸 `JobId=xxx…`）。
5. 「取消生成」生成期间可见可点；点击后 SSE 断开，上传区回到可再上传状态，3D 场景模型不变。
6. 取消时明确提示「云端任务可能仍在继续、额度可能已消耗」。
7. 等待期间侧栏滑杆、预设、视角按钮**全部仍可操作**（不 disabled、不被遮罩覆盖）。
8. 整车与轮毂可**同时**各自生成而互不干扰（两路进度独立显示）。

#### P0-7　失败分级处置（禁止自动降级）

**描述**：按 §2.4.3 六类场景分级处置；下载失败自动重试；轮询超时保留 JobId 提供「继续等待」。

**验收标准**：

1. **反例验收（最重要）**：LIVE 模式下构造任意一种失败（凭证错误 / 断网 / 云端 FAIL / 超时）→ 3D 场景中**绝不可**出现 `my-car.glb` 或 `wheel.glb` 演示模型冒充为"本次生成结果"。
2. 凭证类失败 → 展示 P0-1 三步指引；提供的「改用演示模型看看效果」按钮文案**必须含"演示"二字**。
3. 轮询超时（可设 `MAX_POLL_MS=10000` 快速复现）→ 提供「继续等待 8 分钟」与「放弃」，且「继续等待」携带原 JobId 续等（Network 可见后续 query 用同一 JobId）。
4. 下载失败（临时改坏 `glb.url` 复现）→ 自动重试 2 次，间隔约 2s 与 6s；两次都失败才报错。
5. 重试成功 → 正常走完流程，算 1 次成功（不重复计次）。
6. 云端 FAIL → 提供「用同样参数重试」，点击后使用**同一批图片与参数**重新提交（不需重新选图）。
7. 任何失败后，上一次成功载入的模型**保持原样**；报错文案给出具体原因，不含 `undefined` / `null` 等裸值。
8. 修掉 F11：超时文案**不再**出现「降低面数」（本期面数不可调）。

#### P0-8　生成结果可读命名 + 导出

**描述**：GLB 文件名可读化；提供「导出」按钮把 GLB 下载到本地。

**验收标准**：

1. 新生成文件名格式 `{kind}-{YYYYMMDD-HHmm}-{hash6}.glb`（例 `car-20260829-2145-a1b2c3.glb`），`kind ∈ {car, wheel}`。
2. 时间戳取服务端本地时间，分钟级。
3. 成功后上传区显示「导出 GLB」按钮；点击触发浏览器下载，文件可被 Blender / 系统 3D 查看器正常打开。
4. 整车与轮毂导出按钮互不影响，导出内容各自正确。
5. 文件仍落盘 `.cache/models`（`GET /api/asset/<name>` 可取回），不破坏现有装配链路。

#### P0-9　生成历史索引 + 「我的模型」列表

**描述**：服务端维护 `.cache/models/index.json`；侧栏新增「我的模型」折叠区，可浏览历史并重新载入。

**验收标准**：

1. 每次成功生成后 `index.json` 追加一条，字段含 `name`、`kind`、`size`(bytes)、`createdAt`(ISO)、`imageCount`、`faceCount`、`jobId`。
2. 侧栏出现「我的模型」折叠区，按 `createdAt` **倒序**（最新在最上）。
3. 每条显示：时间（`MM-DD HH:mm`）、类型（整车/轮毂）、体积（如 `44.2 MB`），以及「载入」「导出」按钮。
4. 点「载入」→ 模型载入 3D 场景，效果与刚生成完一致（整车走 `loadCarFromUrl`，轮毂走四轮装配）。
5. **刷新页面后列表不丢失**（数据来自服务端 JSON，非内存）。
6. `.cache/models` 为空时显示空态提示，不报错、不留空白块。
7. 旧的随机名文件（如 `car-a1b2c3d4e5f6.glb`）不崩溃，可正常列出（无 index 记录时从文件名与 stat 兜底）。

#### P0-10　额度与次数统计（失败不计次）

**描述**：服务端 `.cache/usage.json` 记录生成次数，侧栏展示；严格区分"消耗次数"与"失败次数"。

**验收标准**：

1. 侧栏显示「已生成 N 次 · 成功 M 次」（或等价表述），跨页面刷新保留。
2. **只有** `stage:'done' && mode:'live'` 才使消耗次数 +1。
3. 以下一律**不计入消耗次数**：凭证类错误、提交被拒、云端 FAIL、轮询超时、用户取消、DEMO 模式生成。
4. 失败计入独立的「失败」计数或单独展示，不与成功数混算。
5. QA 验证：连续制造 3 次凭证失败 + 1 次成功 → 显示「已生成 1 次」（不是 4 次）。
6. DEMO 模式生成**完全不计数**。

#### P1-1　模型精度档位（标准 / 高精）

#### P1-2　上传前质量预检（警告不阻断）

**描述**：前端纯 JS 预检（无新依赖）：分辨率过低、严重过曝/欠曝 → 黄色警告，可继续。

**验收标准**：

1. 长边 < 1024px → 警告「照片偏小，可能影响细节」。
2. canvas 采样直方图：高亮像素占比 >60% 或暗部占比 >60% → 警告「照片偏亮/偏暗，建议换个光线」。

4. **不阻断**：有警告时仍可提交，警告为黄色（非红色、非模态）。
5. **未引入任何新的 npm 依赖**（`package.json` dependencies 不增加）。

#### P1-3　源图指纹去重

**描述**：前端计算源图指纹，服务端记录；同一组照片重复提交时先提示，避免重复消耗额度。

**验收标准**：

1. 每张图算内容指纹（压缩后 dataUrl 的 SHA-256 前 16 位），多张排序后拼为组合指纹。
2. 组合指纹随请求提交，服务端记入 `index.json`。
3. 再次提交相同组合 → 前端提示「这组照片已生成过（MM-DD HH:mm），是否重新生成？」+「重新生成」/「取消」。
4. 「取消」不提交请求、不计次。
5. 部分相同（5 张中换 1 张）→ 视为新组合，**不提示**。

#### P1-4　磁盘清理与删除

**描述**：「我的模型」支持单条删除；总量超阈值提示清理；不静默删除。

**验收标准**：

1. 每条历史带「删除」，二次确认后删除 GLB 与 index 记录。
2. 超过 20 条或总占用 > 1GB 时，列表顶部显示清理提示（**不自动执行**）。
3. 清理提示提供「保留最近 10 个」一键操作，执行前列出将被删除的条目供确认。
4. 任何情况下不静默删除未超阈值的用户成果。
5. 删除正被 3D 场景载入的模型时给出提示，且场景不崩溃。

---

#### P1-5　`npm run token` 一条命令配置凭证

**描述**：新增脚本把 token 写入 `~/.workbuddy/tokens/hunyuan3d`，免手敲路径。

**验收标准**：

1. `package.json` 增加 `token` 脚本，用法 `npm run token -- tk_xxxxxxxx`。
2. 目录不存在时自动创建 `~/.workbuddy/tokens`。
3. 写入后文件权限 `0600`。
4. 写入成功打印后续提示（「无需重启，页面上点『我已更新』即可」）。
5. 参数缺失或格式不以 `tk_` 开头 → 打印清晰用法并**非零退出**，不写入文件。
6. 不带 `--`（`npm run token tk_xxx`）也能正常工作。

---

#### P1-6　记住上次模型，启动自动载入

**描述**：localStorage 记住上次成功载入的整车/轮毂模型，下次启动优先载入。

**验收标准**：

1. 成功生成或成功载入历史后，把 URL 写入 localStorage（整车、轮毂分开记）。
2. 下次启动优先载入记住的模型，而非固定 `public/models/my-car.glb`。
3. 记住的 URL 失效（`/api/asset/...` 返回 404）→ 自动回退预置模型，**不白屏、不报错弹窗**。
4. 提供「恢复默认模型」入口，可清除记忆回到预置模型。
5. 载入失败兜底到程序化轮毂（与现有 `useProceduralWheel` 逻辑一致）。

## 8. 待确认问题（Open Questions）

> 以下问题的答案会影响实现细节，需在开发前确认。**未确认项按「保守默认」实施，不做乐观假设。**

| # | 问题 | 影响 | 当前默认方案 |
|---|---|---|---|
| Q1 | tempToken 能否从字符串本身解析出过期时间？是否为 JWT？ | 决定 P0-2「预计过期时间」是精确值还是估算值 | tempToken 字符串本身**不可解析**，但凭证返回体带 `tempTokenExpiresAt` 精确字段；token 文件格式需支持携带该过期时间 → 「预计过期时间」显示**精确值**，缺失时降级为 mtime + 16h 估算 |
| Q2 | 本项目是否有服务端可用的 token 刷新接口？ | 决定能否做无感刷新 | 默认**没有**。真实原因：凭据获取能力绑定在 IDE 会话/助手侧，没有暴露服务端可调用的 HTTP 刷新接口，与「调用场景」无关 → 只做引导换票 |
| Q3 | 云端是否有余额 / 配额查询接口？ | 决定 P0-10 是真实余额还是本地估算 | 默认**没有** → 本地计数，文案避免承诺"还剩 X 次" |
| Q4 | 用户取消后云端任务能否主动终止？额度是否退还？ | 决定「取消」按钮的提示文案 | 默认**不能终止、不退还** → 取消时明确告知"额度可能已消耗" |
| Q5 | 混元 3D 的 `ImageBase64` 是否支持数组（多图）？ | 若支持，多视角可极大简化 | 默认**不支持**（单字符串）→ 维持单主视角方案 |
| Q6 | `FaceCount` 合法范围上限？超限是 FAIL 还是自动截断？ | 决定 P1-1 高精档（×1.5）是否安全 | 默认**未知** → 高精档上线前必须实测一次 |
| Q7 | `MultiViewImages` 的 `ViewType` 枚举有哪些？是否必须配齐 front/side/back 才生效？ | 决定 P2-1 的接入成本 | 默认**未知** → 本期不做 |
| Q8 | 结果文件 URL（GLB / preview）有效期多久？ | 决定下载失败重试是否仍有效、preview 图能否归档 | 默认**短期有效（数小时）** → 下载失败重试窗口设 2 次 / 8 秒内；preview 图在生成成功时立即抓取归档 |
| Q9 | 生成的 GLB 是否内嵌 PBR 贴图？44MB 主要是几何还是贴图？ | 决定 P1-1 高精档的体积预期与"导出"文件的可用性提示 | 默认**已开 PBR（`EnablePBR: true`）** → 导出时提示"文件较大（约 30–45MB）" |
| Q10 | 平台对用户上传照片的留存策略？ | 决定隐私声明的准确表述 | 默认**不明** → 隐私文案只写己方可确认的事实（"照片会上传至云端用于生成"），不承诺云端留存时长 |

## 9. 交付与优先级建议

| 阶段 | 范围 | 目标 |
|---|---|---|
| **第一批（必须）** | P0-1、P0-2、P0-4、P0-5、P0-6、P0-7、P0-11 | 回答用户"需要我做什么"，并把等待/失败体验做扎实 |
| **第二批（强烈建议）** | P0-3、P0-8、P0-9、P0-10 | 让用户拿得到、找得回自己的模型，且成本心里有数 |
| **第三批** | P1-1 ~ P1-6 | 体验优化与成本节省 |
| **待评估** | P2-1 ~ P2-4 | 需先回答 Q7 / 隐私方案再决定 |

> **最小可交付（MVP）底线**：P0-1 + P0-2 + P0-4 + P0-7。
> 做到这四条，用户就能「知道自己要做什么 → 换票成功 → 传自己的照片 → 真的生成出来 → 失败时不困惑」。其余是可渐进补齐的体验层。
